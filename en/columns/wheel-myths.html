Is there a winning pattern on the Wheel?

Seven Wheel claims, checked against the server code. No pattern today; before May 2024 the last result hinted at the next one, and some bets paid on average.

Answer

Today, there is no pattern

The winning segment is picked the moment the spin starts, one of 25 segments, each equally likely. Past results, the time, who bet and how much are not used. Before May 2024, though, it worked differently: the last result showed which segments were likely next, and some bets paid on average (see "Before May 2024").

  • 1/25Every segment has the same chance
  • −4%Average return when betting on 1, 3 or 5
  • −16%Average return when betting on 20

Whatever number you bet on, the longer you play, the more you lose. To lose the least, bet on 1.

In this article, the Wheel's segments are called by the numbers shown in the game: 1, 3, 5, 10, 20. The number is the payout multiplier when it wins.

How the Wheel works

One round

  1. Betting open45 secondsScrap can only be placed during this time
  2. Spin startsInstantThe winner is decided and betting closes at the same moment
  3. Spinning13–18 seconds + slowdownIt just turns toward the segment already chosen
  4. PayoutInstantWinning bets are paid, losing bets are removed

The winner is decided before the wheel starts turning. While it spins, the result can no longer change.

What is used to pick the winner, and what is not

Used

  • The number of segments (25)
  • A random generator rebuilt on the spot

Not used

  • The previous round's result
  • The time, the round number
  • The number of players on the server
  • The amount bet
  • Who bet
  • How the wheel spins

In plain words, the spin-start code does this.

When the spin starts:
  make one new seed and rebuild the random generator with it
  winning segment = one of segments 0 to 24, each equally likely
  decide the stop angle and how long it spins
  close betting

The random calls in the actual code

The spin-start code calls the random functions in this order. All of them are built-in methods of Unity and .NET, not a random generator written for Rust.

OrderMethod calledWhat it decides
1UnityEngine.Random.Range(int.MinValue, int.MaxValue)The seed. Takes one integer from Unity's random generator
2new System.Random(seed)Creates a new .NET random generator from that seed
3Next(0, segmentCount)The winning segment. An integer from 0 up to but not including 25, that is, 0–24
4NextDouble()The stop-angle offset (±6 degrees). Made from a decimal from 0 up to but not including 1
5NextDouble()How long it spins (13–18 seconds)

The behavior of each is described in the official documentation.

  • UnityEngine.Random uses a method called Xorshift 128, and its state is one shared state for the whole game. Other code on the server uses the same generator, so its state when the Wheel takes a seed depends on how many times other code has called it before.
  • System.Random(seed) produces the same sequence of numbers from the same seed. The Wheel rebuilds it with a new seed on every spin, so it never continues the previous round's sequence.
  • Next(min, max) includes min and excludes max. Next(0, 25) returns 0–24, so one of the 25 segments is picked directly.
  • NextDouble() returns a decimal from 0 up to but not including 1. It is only used for the angle offset and the spin length, and has nothing to do with the winning segment.

Only line 3 decides the winning segment. Nothing before or after it mixes in past results or the contents of the bets.

1 appears in every other segment, and 20 has only one segment. All 7 wheels checked had the same order.

Chance of winning for each number

  1. 1 (12 segments)48%
  2. 3 (6 segments)24%
  3. 5 (4 segments)16%
  4. 10 (2 segments)8%
  5. 20 (1 segment)4%

The only thing that sets a number's chance is how many segments it has.

A program that behaves the same way

This is a program written from scratch based on the behavior found by reading the code. No game code was copied. The part that picks the winner and the payout part are all there is.

import random

# The order of the 25 segments. The number is the payout multiplier when it wins
SEGMENTS = [3, 1, 10, 1, 3, 1, 5, 1, 5, 3, 1, 10, 1, 3, 1, 5, 1, 3, 1, 20, 1, 3, 1, 5, 1]

def spin(source):
    """One round. Rebuild the random generator with a new seed and pick one of 25 segments, each equally likely"""
    fresh = random.Random(source.getrandbits(32))
    return fresh.randrange(len(SEGMENTS))

def payout(bets, segment):
    """bets is {number: amount bet}. Only the bet on the winning number comes back, times (1 + number)"""
    number = SEGMENTS[segment]
    return bets.get(number, 0) * (1 + number)

Compared with the table above, source.getrandbits(32) is step 1 (take a seed), random.Random(...) is step 2 (rebuild the generator) and randrange(25) is step 3 (pick a segment). The random method is Python's, so the sequence of numbers is not the same as in the game, but the way of picking is the same.

spin has no place to receive the previous result, the time or the contents of the bets. The only input is the random source. Its shape alone shows there is no room for a pattern.

Checking common claims

"20 hasn't come up for a while, so it's due soon"

Doesn't holdThe previous result is not used anywhere. The random generator is also rebuilt every spin. Even if 20 has not come up in 100 spins, the chance of 20 next time is still 4%.

"Watch how the wheel spins and you can tell where it stops"

Too late to betWhere it stops is decided when the spin starts, and betting has already closed by then. The speed during the spin and how it slows down do not change the result. The stop angle wobbles by ±6 degrees and the segments are not all the same width, so on average 0.35% of the time (8% on the thin 1 segment next to 20) the segment closest to the pointer is not the one that pays. The segment that pays is the one decided first.

"Some numbers come up more at certain times or with more players on the server"

No changeThe only thing the winner-picking code uses is the number of segments (25). Neither the time nor the number of players is in it.

"Big bets lose more often"

No effectThe winner-picking code does not look at the amount bet or who bet. The contents of the bets are only read at payout, after the winner is decided.

"The segments next to 20 come up more. The order of the segments matters"

No effectThe winner is picked by "segment index," and every index has a 1/25 chance. Neither the order nor the different segment widths affect the chance. Up to 2024-05-01, the winner was decided where the wheel stopped, so the wide 20 segment came up 4.45% of the time.

"Double your bet after each loss and you'll win in the end"

Same average returnEach result is unrelated to the previous one, so changing the order of bet sizes leaves the average return the same. A losing streak only makes the bet grow fast. Even on 1, losing 10 times in a row happens about 1 in 1,000 times.

"Bet on every number and you can't lose"

Always hits, still losesBetting 1 on each of the 5 numbers, you bet 5 and get 4.6 back on average (−8%). That is because every bet except the winning number is lost that round.

Why it still looks biased

  • 36%Chance of no 20 in 25 spins in a row
  • 2.5%Chance of 1 coming up 5 times in a row (about 1 in 40)

Even when everything follows the odds, results look biased. About 1 time in 3, "no 20 in 25 spins" is exactly what the odds predict. People look for reasons behind streaks and bias, but here there is none.

Before May 2024

In the 2024-05-02 update, the official notes say the "Bandit Camp Wheel's randomness handling was reworked." Reading the code from that time, before the rework the winner was decided differently from today, and the last winning segment showed which segments were likely next.

How it worked back then

  • The winner was not decided first. At spin start, the code only gave the wheel a random speed. The speed dropped on its own, and the segment closest to the pointer where it stopped was the winner.
  • The previous winner was the next starting point. The wheel started the next round facing where it had stopped. The angle turned in one round is "180 × speed + about 212 degrees," so where it stopped, seen from the starting point, depended on the range of the random speed.
  • The range was too narrow, so half a turn was biased. With a speed of 7–10, the turn angle had a range of 540 degrees (1.5 turns). One full turn of that lands on every segment equally, but the remaining half turn lands only on the side 3–14 segments past the previous winner. So those 12 segments were about 2 times as likely to win. From 2023-05-04 the speed became 7–16, the range widened to 4.5 turns, and the bias got smaller.
  • Segment widths differed. Because the segment closest to the pointer won, the angle range that made each segment win differed, from 11.6 to 16.2 degrees. The 20 segment was wide at 16.0 degrees and won 4.45% of the time even without watching the previous result (4% today). The segment positions were the same in the 5 versions that could be read (the game client from 2018-12, 2020-11, 2021-08 and 2024-04, and today's server).

How certain the prediction claim is

  • What the code shows. Up to 2024-05-01, the direction the wheel stopped at carried over to the next round, and the random range of the turn angle was only 1.5 turns (4.5 turns from 2023-05-04). So knowing the previous winner tells you which segments are likely next. From 2024-05-02, the winner is picked equally from 25 segments with a random generator rebuilt every spin, and neither the previous result nor the wheel's direction is used.
  • What was calculated. The return values are calculations using the actual segment positions, the spin direction and the tick length. The segment positions were read from the game data, and the spin direction was derived from those positions. They are not values counted by spinning in the game.

Changes after the rework

After the 2024-05 rework, up to today (2026-11), the way the winner is decided, how the wheel spins, how the pointer is read and the multipliers have not changed. The only changes are an added check at payout that the betting terminal still exists, and small differences in how the code is called; neither affects the chances.

What we don't know

  • 2018-08 to 2018-12. For the first 4 months after the Wheel was added, neither the game client nor the server could be read.
  • Server, 2018-12 to 2020-04 and 2020-11 to 2021-04. The server code from these periods could not be read, so the range of the spin-start speed is unknown. Since 2020-11 and 2021-04 at either end are the same, 2020-11 to 2021-04 is assumed to be the same as well.
  • Spin direction. From the segment positions, the direction was derived as the one where the segment under the pointer moves toward lower indices when the wheel turns. Whether that is clockwise or counterclockwise on screen has not been checked.
  • Can the seed be guessed from outside? The seed is made from a random generator inside the server and is not sent to players. It is assumed that it cannot be guessed from outside, but this is an estimate.
  • Scope of this article. The PC server, version 2026-11-07. Future updates may change this.

How this was checked

The server's own code (the intermediate code of the Wheel class) was read, and the settings of the Wheel and the betting terminals were read from data files. The server was not started. The multipliers (1, 3, 5, 10, 20), the number of segments, the 45-second betting window and the 13–18 second spin were all read values. The chances and average returns are calculated from them.

For the code before May 2024, the server code of the time was read from builds of Oxide, a modding framework. From 2021-04 these were GitHub releases; for 2020-04 to 2020-11, builds saved on the Wayback Machine. Oxide ships the game's code with its own hook calls inserted. For the current version, the Wheel code in Oxide's build and in the game's build was confirmed to be the same apart from the inserted hooks. Builds from 2020-04 to 2026-11 were compared to narrow down when things changed. Segment positions and how the winner is read were also checked in the game client versions from 2018-12, 2020-11, 2021-08 and 2024-04. The bias and returns of that time are values summed over fine divisions of the spin-start speed and the stopped position, using a program that behaves the same way (old in wheel-myths.py).

These are not results counted by actually spinning in the game. They confirm what the code says. The 100,000-spin results in this article come from running a self-written program that behaves the same way.
