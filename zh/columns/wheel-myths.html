Big Wheel 转盘有必胜规律吗？

我们根据阅读服务器代码的结果，逐一检验关于 Bandit Camp 转盘的 7 种说法。现在没有任何规律。2024 年 5 月之前，看上一次开出的格就能知道下一次更容易开出哪些格，也存在平均下来能赚的下注方式。

结论

现在，没有任何规律

开出的格在开始转动的那一刻，从 25 个格中以相等的概率选出 1 个。上一次的结果、时间、下注的人和金额都不会被用到。不过在 2024 年 5 月之前，机制不同：看上一次开出的格就能知道下一次更容易开出哪些格，也存在平均下来能赚的下注方式（见“2024 年 5 月之前”）。

  • 1/25每个格的概率都相同
  • −4%押 1、3、5 时的平均返还
  • −16%押 20 时的平均返还

无论押哪个数字，玩得越久亏得越多。想让亏损最小，就押 1。

本文用与游戏内显示相同的数字 1、3、5、10、20 来称呼转盘上的格。数字就是开中时的赔付倍率。

转盘是这样运作的

一轮的流程

  1. 接受下注45 秒只有这段时间可以放 Scrap
  2. 开始转动一瞬间决定开出的格，同时截止下注
  3. 转动13～18 秒 + 减速只是朝着已经决定的格转过去
  4. 赔付一瞬间押中的返还，没押中的消失

开出的格在转盘开始转动之前就已决定。转动期间，结果已经不会再变。

决定开出的格时用到的和没用到的

用到的

  • 格的数量（25）
  • 当场重新生成的随机数

没用到的

  • 上一轮的结果
  • 时间、轮次编号
  • 服务器的人数
  • 下注金额
  • 下注的人
  • 转盘的转法

把开始转动时的代码用文字写出来，就是这样。

开始转动时:
  生成 1 个新的种子，用这个种子重新生成随机数
  开出的格 = 从 0 号到 24 号中以相等的概率选 1 个
  决定停下的角度和转动时间的长短
  截止下注

实际代码调用的随机数

开始转动时的代码按以下顺序调用随机数。全部是 Unity 和 .NET 自带的方法，并不是 Rust 自己写的随机数。

顺序调用的方法决定什么
1UnityEngine.Random.Range(int.MinValue, int.MaxValue)种子。从 Unity 的随机数取 1 个整数
2new System.Random(种子)用这个种子新建一个 .NET 的随机数
3Next(0, 格数)开出的格。大于等于 0、小于 25 的整数，即 0～24
4NextDouble()停下角度的偏移（±6 度）。由大于等于 0、小于 1 的小数生成
5NextDouble()转动时间的长短（13～18 秒）

各自的性质都写在官方文档里。

  • UnityEngine.Random 采用名为 Xorshift 128 的方式，整个游戏共用 1 个状态。服务器里的其他代码也用同一个随机数，所以转盘取种子时的状态，取决于其他代码在此之前调用了多少次。
  • System.Random(种子) 从同一个种子会生成同样的数列。转盘每转一次都用新的种子重新生成，所以不会接着上一轮的数列往下走。
  • Next(最小, 最大) 包含最小值，不包含最大值。Next(0, 25) 返回 0～24，25 个格中的某一个被直接选中。
  • NextDouble() 返回大于等于 0、小于 1 的小数。只用于角度偏移和转动时间，与开出的格无关。

决定开出的格的，只有第 3 行。在它前后，没有任何混入上一次结果或下注内容的处理。

行为相同的程序

这是根据读代码弄清的行为、自己从零写的程序，没有照抄游戏代码。决定开出的格的部分和赔付的部分就只有这些。

import random

# 25 个格的排列。数字是开中时的倍率
SEGMENTS = [3, 1, 10, 1, 3, 1, 5, 1, 5, 3, 1, 10, 1, 3, 1, 5, 1, 3, 1, 20, 1, 3, 1, 5, 1]

def spin(source):
    """一轮。用新的种子重新生成随机数，从 25 个格中以相等的概率选 1 个"""
    fresh = random.Random(source.getrandbits(32))
    return fresh.randrange(len(SEGMENTS))

def payout(bets, segment):
    """bets 是 {数字: 下注金额}。只有押中数字的赌注会以 (1 + 数字) 倍返还"""
    number = SEGMENTS[segment]
    return bets.get(number, 0) * (1 + number)

与上面表格的对应关系是：source.getrandbits(32) 是第 1 步（取种子），random.Random(...) 是第 2 步（重新生成随机数），randrange(25) 是第 3 步（选格）。随机数的方式是 Python 的，所以生成的数列与游戏不同，但选法相同。

spin 里没有接收上一轮结果、时间或下注内容的地方，传进来的只有随机数的来源。从结构上也能看出，规律没有产生的余地。

检验常见说法

“20 好久没出了，差不多该出 20 了”

不成立上一轮的结果在任何地方都没有被用到。随机数也是每转一次就重新生成。即使 20 已经 100 次没出，下一次出 20 的概率仍然是 4%。

“看转盘的转法，就能读出它停在哪里”

读得出也押不了停下的位置在开始转动时就已决定，而那一刻下注已经截止。转动途中的速度和减速方式都不会改变结果。停下的角度会有 ±6 度的摆动，格的宽度也不一致，所以平均有 0.35% 的情况（20 旁边那条窄的 1 格为 8%），看上去离指针最近的格与实际赔付的格不同。赔付的是事先决定的那一格。

“不同时间段或服务器人数不同，容易开出的数字会变”

不会变决定开出的格的代码只用到格的数量（25）。时间和玩家人数都不在其中。

“押得大就容易不中”

没有关系决定开出的格的代码既不看下注金额，也不看是谁下的注。下注内容只在开出的格决定之后的赔付时才会被读取。

“20 旁边的格容易出。格的排列有讲究”

没有关系开出的格是按“格的编号”选的，每个编号都是 1/25。排列和格宽的不同都与开中难易无关。到 2024-05-01 为止，开出的格由停下的位置决定，所以较宽的 20 格开出的比例是 4.45%。

“没中就加倍再押，最后总能赢”

平均返还不变每次的结果都与上一次无关，所以改变下注金额的顺序，平均返还也一样。连续不中时，只有赌注会急剧增加。即使押 1，连续 10 次不中的情况大约每 1,000 次就会发生 1 次。

“所有数字都押，就不会输”

一定会中，但平均会亏在 5 个数字上各押 1，押了 5，平均返还 4.6（−8%）。因为除了开中的数字以外，其余赌注在那一轮都会消失。

为什么看起来仍然有偏差

  • 36%连续 25 次都不出 20 的概率
  • 2.5%1 连出 5 次的概率（大约 40 次中有 1 次）

即使完全按概率来，结果看起来也会有偏差。大约每 3 次就有 1 次“转了 25 次都没来 20”，这正是概率本来的样子。人们会为连出和偏差寻找原因，但这里没有原因。

2024 年 5 月之前

在 2024-05-02 的更新中，官方写道“重做了 Bandit Camp 转盘随机数的处理方式”。阅读当时的代码可以发现，重做之前决定开出的格的方式与现在不同，看上一次开出的格就能知道下一次更容易开出哪些格。

当时的机制

  • 开出的格并不是事先决定的。 开始转动时，代码只是给转盘一个随机的速度。速度会自然下降，停下时离指针最近的格就是开出的格。
  • 上一次开出的格就是下一次的起点。 转盘保持停下时的朝向开始下一轮。一轮转过的角度是“180 × 速度 + 约 212 度”，所以从起点看停下的位置，取决于速度随机数的范围。
  • 范围不够，半圈产生了偏差。 速度为 7～10 时，转过角度的范围是 540 度（1.5 圈）。其中 1 整圈平均落在每个格上，但剩下的半圈只会落在上一次开出的格往前 3～14 格的那一侧。所以这 12 个格开中的概率大约是 2 倍。从 2023-05-04 起速度变为 7～16，范围扩大到 4.5 圈，偏差变小了。
  • 格的宽度不同。 由于离指针最近的格算开中，各格对应的开中角度范围从 11.6 到 16.2 度不等。20 的格宽达 16.0 度，即使不看上一次结果下注，开中比例也有 4.45%（现在是 4%）。格的位置在能读到的 5 个版本（2018-12、2020-11、2021-08、2024-04 的游戏客户端，以及现在的服务器）中都相同。

能否预测的可信度

  • 从代码能说明的。 到 2024-05-01 为止，停下时的朝向会原样保留到下一轮，而转过角度的随机数范围只有 1.5 圈（2023-05-04 起为 4.5 圈）。所以只要知道上一次开出的格，下一次更容易开出的格就确定了。从 2024-05-02 起，开出的格用每转一次就重新生成的随机数从 25 个格中等概率选出，上一次的结果和转盘的朝向都不会被用到。
  • 通过计算得出的。 返还的值是用格的实际位置、转动方向和 1 帧的长度计算出来的。格的位置从游戏数据中读取，转动方向由这些位置推算得出。这些不是在游戏里实际转动后数出来的值。

重做之后的变化

2024-05 重做之后，到现在（2026-11）为止，决定开出的格的方式、转法、读取指针的方式和倍率都没有变。变化的只有：赔付时增加了确认下注终端是否存在的处理，以及代码调用方式上的细微差别，都与开中难易无关。

尚不清楚的地方

  • 2018-08 至 2018-12。 转盘加入后的最初 4 个月，游戏客户端和服务器代码都未能读到。
  • 服务器的 2018-12 至 2020-04 和 2020-11 至 2021-04。 这些时期的服务器代码未能读到，所以不清楚开始转动时速度的范围。由于 2020-11 和 2021-04 两端相同，我们认为 2020-11 至 2021-04 期间也相同。
  • 转动方向。 根据格的位置，推算出转动时指针下方的格朝编号较小的一侧移动。在画面上是顺时针还是逆时针，尚未确认。
  • 种子能否从外部猜中。 种子由服务器内部的随机数生成，不会发送给玩家。我们认为无法从外部猜中，但这是推定。
  • 本文的对象。 2026-11-07 版本的 PC 版服务器。今后的更新可能会改变这些内容。

调查方法

我们阅读了服务器本体的代码（转盘类的中间代码），并从数据文件中读取了转盘和下注终端的设置值。没有启动服务器。倍率（1、3、5、10、20）、格数、45 秒的下注时间、13～18 秒的转动时间，都是读到的值。概率和平均返还是由此计算出来的。

2024 年 5 月之前的代码，读的是 MOD 框架 Oxide 的发布包中所含的当时服务器代码。2021-04 起来自 GitHub 的 Releases，2020-04 至 2020-11 来自 Wayback Machine 保存的发布包。Oxide 会在游戏代码中插入自己的调用后再发布。我们在当前版本中确认了，除插入的部分外，Oxide 包中和游戏本体中的转盘代码相同。我们对比了 2020-04 到 2026-11 的发布包，缩小了发生变化的时间点。格的位置和读取开出格的方式，也在 2018-12、2020-11、2021-08、2024-04 版本的游戏客户端中确认过。当时的偏差和返还，是用行为相同的程序（wheel-myths.py 中的 old），把开始转动时的速度和停下的位置细分后累加得出的值。

这些不是在游戏中实际转动后数出来的结果，而是对代码如何编写的确认。文中 10 万次的结果，是运行自己编写的、行为相同的程序得到的。
